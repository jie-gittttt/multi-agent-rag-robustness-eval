1. 逐攻击类型诊断

关键词替换


脆弱根因：模型对问题表述的微小变化（同义改写、句式重组）敏感，导致检索到不完整或偏离的上下文，或生成回答时丢失关键细节。从案例看，对抗问题将“最大的不同是什么”改为“核心区别体现在哪些方面”，模型虽然提取了正确信息，但回答因列举项未完成而降低了忠实度（faithfulness 从 1.0 降至 0.69）；另一个案例中，对抗问题用“终止参与后续减排阶段”替换“退出第二承诺期”，答案相关性（answer_relevancy）从 0.94 降至 0.73。受影响指标：answer_relevancy、faithfulness 下降。

语义干扰


脆弱根因：对抗问题通过引入无关或误导性假设（如“是否反映了空气质量指数”）破坏问题语义，模型无法区分事实查询与逻辑陷阱，直接拒绝回答。案例中模型输出“无法回答”，导致 answer_relevancy 和 context_precision 均降至 0。受影响指标：answer_relevancy、context_precision 严重下降，faithfulness 因拒绝回答而出现异常（通常降低或变为 0.5 等效值）。

上下文劫持


脆弱根因：检索到的多个文档包含冲突答案（如无大气层时地球表面温度 -18℃ vs -27.3℃），模型缺乏冲突消解机制，只能列出矛盾信息或声称“无法给出唯一答案”，导致 answer_relevancy 降为 0。即使每个文档自身忠实，整体回答对用户无帮助。受影响指标：answer_relevancy 急剧下降，context_precision 轻微降低。

先验冲突


脆弱根因：与上下文劫持类似，但冲突来自文档中故意植入的“先验错误”信息。模型尝试整合时无法判定权威性，最终返回“无法确定唯一答案”，同样使 answer_relevancy 归零。案例中 faithfulness 从 1.0 降至 0.83（因回答部分正确），但 context_precision 也从 0.7 降至 0.67。受影响指标：answer_relevancy 严重下降，faithfulness 和 context_precision 波动。

无关噪声注入


脆弱根因：检索器将大量无关噪声文档混入上下文，模型虽未直接编造，但会错误地从噪声文档中提取信息（如案例中引用噪声文档里的正确数字，但来源错误），或噪声稀释了相关文档的权重，导致 context_precision 大幅下降（案例中从 1.0 降至 0.33、0.42），同时 answer_relevancy 也因噪声干扰而降低。受影响指标：context_precision 严重下降，answer_relevancy 中度下降。

排序污染


脆弱根因：调整文档排序使无关或低质量文档排在前面，模型优先使用排名靠前的文档（即使该文档包含正确答案，但来源编号错误），导致 faithfulness 和 context_precision 归零或极低。例如案例中模型回答“根据文档5”而非正确的“文档1”，虽然内容正确但引用错误，faithfulness 被判为 0。受影响指标：faithfulness、context_precision 严重下降，context_recall 不受影响。 ---

2. 跨攻击模式归纳

  • 共享根因：检索结果质量不可控

    • - 上下文劫持、先验冲突、排序污染、无关噪声注入均涉及检索阶段返回了错误、冲突或排序异常的文档，暴露出检索器缺乏去重、冲突检测、质量排序等机制。
  • 共享根因：模型缺乏逻辑推理与鲁棒理解能力

    • - 语义干扰、关键词替换、先验冲突中，模型对问题中的否定、假设、同义改写或隐含冲突缺乏深度理解，无法正确解析用户真实意图。
  • 独立根因：冲突消解缺失

    • - 上下文劫持和先验冲突需要模型从多个矛盾文档中判断最可信答案，但模型当前只做机械拼接，无法进行交叉验证。
  • 独立根因：文档引用追踪不严谨

    • - 排序污染和无关噪声注入中，模型盲目信任排名，而不验证引用来源的合理性，导致忠实度被破坏。 ---

    3. 按优先级排序的修复建议

    建议 1：引入冲突检测与多文档一致性校验


  • 针对攻击类型：上下文劫持、先验冲突

  • 具体措施：在检索后、生成前，对返回的多个文档进行语义相似度与数值一致性比对。若发现关于同一事实的表述存在显著差异，则触发冲突消解流程：要么使用多数投票，要么根据文档来源权重或更新时间决定采纳哪个答案，并在回答中注明可能的不确定性。

  • 预期效果：消除因文档冲突导致的“无法给出唯一答案”或矛盾列举，提升答案相关性与忠实度。

    • 建议 2：增强检索器的抗噪声与排序鲁棒性


  • 针对攻击类型：无关噪声注入、排序污染

  • 具体措施：

    • 1. 在检索阶段增加文档质量预过滤（如惩罚长度过长、与问题语义相关性低于阈值的文档）。
    2. 对检索结果进行重新排序时，引入答案完整性校验：优先保留直接包含问题中关键实体和数值的文档，而非单纯依赖向量相似度。
    3. 限制召回数量（如 top-k 适当减小），并允许模型在生成时对每个文档的引用来源进行显式验证（如“根据文档X，答案为Y”），若多个文档给出同一答案则可合并。
  • 预期效果：大幅提高 context_precision，降低对排序和噪声的敏感度。

    • 建议 3：对问题进行语义归一化与逻辑解析


  • 针对攻击类型：关键词替换、语义干扰

  • 具体措施：在生成回答前，使用一个独立的问题理解模块（如较小的大模型或规则引擎），将用户问题转换为标准化的查询形式：

    • - 消解同义表述（如“核心区别” -> “最大的不同”）。
    - 识别并移除逻辑陷阱（如“是否不体现” -> 转换为否定查询，或提示模型忽略误导性假设）。
    - 对包含假设或否定的问题，强制模型先判断是否与文档一致，若不一致则明确拒绝。
  • 预期效果：提升 answer_relevancy 和 faithfulness，减少因措辞变化导致的回答偏差。

    • 建议 4：训练模型对冲突与噪声的显式拒绝能力


  • 针对攻击类型：语义干扰、先验冲突、上下文劫持

  • 具体措施：在微调阶段加入对抗样本，使模型学会输出诸如“上下文存在不一致，无法给出可靠答案”或“问题中包含无法验证的假设，请重新提问”等安全响应，而不是勉强生成。同时，引入一个后处理校验器，对生成的回答进行事实一致性检测（如用另一个小型 NLI 模型检查回答是否完全受上下文支持）。

  • 预期效果：避免模型在不确定时编造答案，同时提高用户对系统边界的信任。

    • 建议 5：建立文档引用溯源与可信度评分机制


  • 针对攻击类型：排序污染、无关噪声注入

  • 具体措施：每个文档在入库时分配唯一 ID 和元数据（如来源、时间戳、可信等级）。模型生成回答时必须明确引用 ID，系统在展示回答后，自动高亮并链接到原始文档。利用用户反馈（如“这个引用是否正确？”）逐步调整文档可信度，并动态影响排序权重。

  • 预期效果：从机制上杜绝模型错误引用文档，同时为排序污染提供反馈回路，逐步提高检索质量。

    4. 系统整体评估

    该 RAG 系统在常规查询下表现良好（高 faithfulness 和 answer_relevancy），但面对六类对抗攻击时鲁棒性不足。主要薄弱点在于：检索阶段缺乏质量控制和冲突消解，生成阶段缺乏逻辑推理与语义鲁棒性，导致上下文劫持、语义干扰等攻击能轻易使答案相关性归零，而排序污染和噪声注入则严重破坏上下文精确度。整体而言，系统目前仅能应对直白、单一来源的问答，在真实复杂场景（如多文档冲突、用户措辞变化、检索干扰）下可靠性显著下降，亟需通过上述修复措施提升安全性。
